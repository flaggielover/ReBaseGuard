Observation monitor prototype and pipe failure handling (development only)

Base: 9b5613d321b29264bd9ed48a1ac8ff02c81db943. Original candidate,
repair, session and interoperability records remain historical and unchanged.

What is implemented
- ObservationMonitor binds each signed payload to the immutable DevSession
  baseline and the last successful observation, then runs the existing start/
  monitor diagnostics. A valid signature alone never permits continuation.
- Initial baseline checks must pass. Busy, stale, unknown-visibility, changed
  identity, invalid-signature, session, storage or transport failures latch stop.
  The latch has no reset API. Clearing a consumer's Event cannot clear it.
- An optional explicitly started watchdog watches a monotonic deadline in its
  own thread. It can set stop_requested while verification or diagnostic fsync
  is blocked; it acquires neither the session nor operation lock to publish stop.
  Polling is 0.01..1 seconds, with 0.25 seconds as the default. This polling
  latency is disclosed; there is no claim of instantaneous OS scheduling.
- The 105-second development deadline retains sample + gap allowances. Issuing
  another challenge never extends it. Evidence age reduces the next deadline,
  so a delayed arrival is not a fresh 105-second window. Request the next sample
  promptly: adding another 60-second sleep between 60-second collections can
  exhaust this conservative deadline. This is a proposal, not a claim of exact
  equivalence with an accepted native-host monitoring loop.
- Diagnostic decisions are fsynced into the existing session journal before a
  successful diagnostic response. A watchdog stop during that I/O prevents a
  successful response even if the earlier diagnostic was green.
- The synthetic Windows pipe client now serializes complete transactions,
  refuses reuse after request failure/closure, closes stdout/stderr even when
  child cleanup times out, and preserves an idempotent close result. A cleanup
  timeout is still an error: closing descriptors does not prove Windows exited.

What this does not implement
stop_requested is a development event, not a signal to a production workload.
There is no launcher, evaluator, host collector, OS policy change or process
termination in ObservationMonitor. A controlling transport must call bridge_failed
on EOF/timeout, and an independently reviewed execution controller must actually
stop its owned work. Authentication/privilege isolation, complete lifetime and
protected-process visibility, guest/host attribution, host durability, route
acceptance and actual-run authorization remain outstanding. No 6-hour or
31.5-hour guarantee is claimed. Every response retains BLOCKED/false.

Starting and stopping
Create the development session in a new p309-wsl-dev-* directory outside Git,
construct the monitor from it, and explicitly call start_watchdog() for autonomous
liveness checks. Without that call, only explicit poll/challenge/accept calls
check liveness; status reports watchdog_active to distinguish the modes.
Always observe stop_requested. Bound transport operations and allow them to
return before close(); Python does not safely cancel blocked worker threads.
Only ephemeral synthetic keys/observations are authorized for these examples.
