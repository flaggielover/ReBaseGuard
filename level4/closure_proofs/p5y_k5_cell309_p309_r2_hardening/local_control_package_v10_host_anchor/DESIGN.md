# Host anchor implementation and exact boundary

The trusted boundary includes Windows administrator/SYSTEM, the pinned controller implementation, and the later independently verified guest root broker/VM lifetime factory. Guest relay/worker and disk snapshots are not host state authorities. Host-administrator whole-disk rollback, compromised guest root, dishonest storage firmware, and hardware attestation are not solved by this library.

The installer will separately enroll one fixed DEVELOPMENT_IDLE_ONCE permitID/epoch, package/guest/runtime/policy/monitor/checkpoint/approval digests, controller/core hashes, exact journal file identity, host ACK public/key-identity pins and independently enrolled guest root public pin. Enrollment revision 3 deliberately contains no actual G: the trusted guest root broker creates G/challenge and a durable local pre-start fence, then signs the fixed pre-start purpose. The real VM/H2 factory must verify that proof against the independently enrolled key and current owned VM/boot/lifetime before it can construct `VerifiedVmReservation`.

`OpenInstalled(vm)` verifies the fixed Controller virtual TokenUser, enabled and restricted service SID, no thread impersonation, SCM OWN_PROCESS/RUNNING/self PID/exact image/account/SID type, exact token privilege set and SCM RequiredPrivileges `{SeChangeNotifyPrivilege}`, protected code/config custody and byte pins, every directory ancestor, NTFS, non-reparse and single-link fixed objects, and the installer's journal volume/file ID. Those are real production implementations, never executed by the temporary tests. Configuration/image/token/process/SCM/file handles are held. Revalidation occurs before journal transitions and ACK signing; a status snapshot is not a new identity proof.

The installer must write a full non-sparse/non-compressed 4096-byte journal: one 512-byte ENROLLED record plus seven zero slots. Runtime only opens this existing file, share mode zero, with WRITE_THROUGH. It never creates/extends/truncates/resets/rearms that file. Logical append writes the next preallocated zero slot, verifies hash-chain/CAS, flushes the same file handle and rereads exact recorded bytes. Any physical truncation, even on a record boundary, missing header, nonzero slot after a gap, hash/schema/binding/state error, replaced file ID, hard link, or unexpected epoch refuses use.

The initial ENROLLED header binds the enrollment hash. The first SESSION_CLAIMED record binds `P309_HOST_ANCHOR_BINDING/3` containing enrollment hash, broker-created G, pre-start proof hash, actual host/guest boot, challenge and held-VM lifetime digest. Every subsequent record uses that bound hash. A different authenticated G/proof on a later open cannot rebind the old claim. This first claim is flushed before returning the anchor. Any persisted claim/partial/prior terminal record on cold start refuses continuation; it is not a new permit.

Sequence 2 RESERVED consumes the one prospective idle permit before OS worker start. Only an opaque verified lease matching the initial claim can supply its evidence digest. The purpose-only signer may produce one session context and one reserve ACK from that record. BindOnce requires that the signer actually produced the reserve ACK, plus an independently verified blocked-invocation lease matching the same reservation. Sequence 3 CONSUMED_BOUND records that root proof's canonical body hash. Only then is opaque `RecordedConsumption` created for one final ACK signing attempt. No supplied next-state string, command, PID, unit, arbitrary bytes, authority setter, reset, rearm, formal grant or successful cleanup API exists.

The journal state graph is ENROLLED → SESSION_CLAIMED → RESERVED → CONSUMED_BOUND. Any live state may become STOP_REQUESTED or RECOVERY_UNKNOWN; STOP_REQUESTED may only upgrade to RECOVERY_UNKNOWN. Unknown is terminal. The component never reports STOPPED because it does not own the real Job/guest manager cleanup proof.

`RequestStop()` is a single irreversible Interlocked exchange, with no journal lock, native I/O, CNG, SCM or cleanup wait. A caller must immediately stop its already-held owned Job/instance independently; `PersistStopRequest`, `MarkRecoveryUnknown`, and Dispose may wait and must not be on that hot stop path. Reserve/bind flush and signing revalidation end with atomic comparisons against the same latch. Late I/O/CNG completion cannot clear it. A receipt's `IsCurrentAtRead` is an instantaneous comparison, never a cacheable dispatch capability. Any future actual dispatch needs the independently supervised owned-instance gate.

`Snapshot.State` is the in-memory safety projection; `PersistedState`, Sequence and HeadSha256 describe the last verified journal record. A failed write may therefore produce memory UNKNOWN with an older persisted STOP_REQUESTED. `ProductionFactoryVerifiedAtOpen` reports factory provenance, not current liveness, collector readiness or dispatch authority.

Receipt publication uses native CREATE_NEW, file flush, and same-handle SetFileInformationByHandle no-replace rename, followed by file flush and exact final-path/readback checks. Directory handles use GENERIC_READ and share read/write but never share delete: native tests showed that omitting share-write prevents legitimate child rename. This pins deletion/rename identity; it does not deny every metadata mutation. Owner/DACL/reparse checks provide the separate custody requirement. Published receipt names are evidence, not the one-use fence.

File flush success means the Windows API completed the requested flush. No portable directory-fsync equivalent, storage power-loss theorem, volume flush, or absolute maximum OS-call latency is claimed. The authoritative slots already exist in an installer-enrolled allocation, reducing dependence on newly published namespace entries. A crash before the first claim leaves no distinguishable claim and cannot be detected by a journal that was never written; no reservation ACK/start authority has yet been returned then. Successful flush is not protection against malicious/full host-disk rollback or hardware that discards acknowledged writes.

The Controller ACK key is distinct from Observer facts signing. The factory opens only `ReBaseGuardP309.Controller.AnchorAck.v1` in Microsoft Software Key Storage Provider, MachineKey+Silent, RSA3072, signing-only, no private export, protected trusted owner/DACL, fixed unique-name hash and SPKI pin. It never generates/imports/repairs a key. An unsupported/missing key or unverified VM/root proof is refusal. The current assembly deliberately has no production implementation of the internal VM lease interfaces; the following real VM service/H2 component must supply it before this package can participate in any installed chain.
