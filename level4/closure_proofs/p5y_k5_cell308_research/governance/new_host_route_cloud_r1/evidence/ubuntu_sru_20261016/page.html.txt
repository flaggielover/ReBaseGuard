<section id="about-kernel-stable-release-updates-sru">
<h1>About kernel stable release updates (SRU)<a class="headerlink" href="#about-kernel-stable-release-updates-sru" title="Link to this heading">¶</a></h1>
<p>Every supported kernel for an Ubuntu release is part of a Stable Release Updates
(SRU) cycle. The Ubuntu Kernel <a class="reference internal" href="../../reference/glossary/#term-SRU"><span class="xref std std-term">SRU</span></a> is a structured procedure to ensure
that kernel updates in Ubuntu’s stable releases are both reliable and
non-disruptive to users.</p>
<p>This document aims to provide an overview about the various aspects of the
Ubuntu kernel SRU process.</p>
<section id="sru-purpose">
<h2>SRU purpose<a class="headerlink" href="#sru-purpose" title="Link to this heading">¶</a></h2>
<p>Kernel SRU focuses on delivering necessary updates without changing core
functionalities with low potential of introducing regressions in stable Ubuntu
releases. This typically covers:</p>
<ul class="simple">
<li><p>Upstream stable updates</p></li>
<li><p>Bug fixes that address relevant issues or improve system stability</p></li>
<li><p>Common Vulnerabilities and Exposures (CVE) security updates</p></li>
<li><p>Hardware enablement (HWE) patches</p></li>
</ul>
</section>
<section id="sru-cycle-cadence">
<span id="id1"></span><h2>SRU cycle cadence<a class="headerlink" href="#sru-cycle-cadence" title="Link to this heading">¶</a></h2>
<p>Since August 2023, the Ubuntu Kernel team has adopted a 4/2 Kernel SRU cycle to
improve predictability and responsiveness. It involves a 4-week (“4/”) stable
update cycle for regular fixes and features, combined with an additional
mid-cycle 2-week (“/2”) update focused on urgent CVE security patches and
critical fixes. This approach enables more timely updates for critical issues
while maintaining stability, and continues to support mid-cycle
<a class="reference internal" href="#exp-sru-kernel-respins"><span class="std std-ref">respins</span></a> for regression fixes as needed.</p>
<figure class="align-default" id="id2">
<img alt="Ubuntu kernel life cycle stages and ideal SRU 4/2 cadence timeline" src="../../_images/exp-kernel-sru-lifecycle-stages.svg" />
<figcaption>
<p><span class="caption-text">Ubuntu kernel life cycle stages and ideal SRU 4/2 cadence timeline</span><a class="headerlink" href="#id2" title="Link to this image">¶</a></p>
</figcaption>
</figure>
<p>See the <a class="reference external" href="https://kernel.ubuntu.com/">Ubuntu Kernel Team</a> home page for details on SRU cycle dates.</p>
<div class="admonition important">
<p class="admonition-title">Important</p>
<p>While the Ubuntu kernel team strives to meet the SRU cycle 4/2 cadence, please
note that SRU cycle dates are tentative. As such, they cannot be guaranteed and
may be subject to change.</p>
</div>
</section>
<section id="sru-patch-submission-and-review-process">
<h2>SRU patch submission and review process<a class="headerlink" href="#sru-patch-submission-and-review-process" title="Link to this heading">¶</a></h2>
<p>All updates that are applied to stable kernels go through the following patch
submission and review process. More details can be found at
:doc:<code class="docutils literal notranslate"><span class="pre">./stable-patch-format</span></code>.</p>
<section id="patch-creation">
<h3>Patch creation<a class="headerlink" href="#patch-creation" title="Link to this heading">¶</a></h3>
<p>The first step for every SRU is to create a patch containing all the necessary
information, including a link to the associated public Launchpad bug report that
contains the SRU justification.
The only exception to this are CVE fixes, where only the CVE number is required.</p>
<p>See the <a class="reference external" href="https://wiki.ubuntu.com/KernelTeam/KernelUpdates">Ubuntu Wiki - Kernel Updates</a> for more information on the SRU
requirements and justification.</p>
</section>
<section id="patch-submission">
<h3>Patch submission<a class="headerlink" href="#patch-submission" title="Link to this heading">¶</a></h3>
<p>Next, contributors send the stable patches to the Ubuntu Kernel Team mailing
list (<a class="reference external" href="mailto:kernel-team&#37;&#52;&#48;lists&#46;ubuntu&#46;com">kernel-team<span>&#64;</span>lists<span>&#46;</span>ubuntu<span>&#46;</span>com</a>) for review.
Where appropriate, the patch should also be submitted to upstream stable in
parallel.</p>
</section>
<section id="mailing-list-review">
<h3>Mailing list review<a class="headerlink" href="#mailing-list-review" title="Link to this heading">¶</a></h3>
<p>Stable patch sets on the mailing list (ML) are then carefully reviewed by the
Ubuntu Kernel Team.
This review process involves validating that the patch fixes the intended
issues, ensuring no regressions are introduced to the kernel, evaluating the
risk and relevance of including the patch into a stable release, and
reconciling mainline and Ubuntu-specific changes.</p>
</section>
<section id="patch-acceptance">
<h3>Patch acceptance<a class="headerlink" href="#patch-acceptance" title="Link to this heading">¶</a></h3>
<p>Once a mailing list patch has been vetted and has at least two <code class="docutils literal notranslate"><span class="pre">ACK</span></code>s from
senior members of the Ubuntu Kernel Team, the commit will then be applied to the
associated stable Ubuntu kernel tree.
The patch will then be considered for release in an upcoming SRU cycle if all
the patch acceptance criteria are met.</p>
<p>See the <a class="reference internal" href="../../reference/patch-acceptance-criteria/"><span class="doc">Ubuntu patch acceptance criteria</span></a>
for more information.</p>
</section>
</section>
<section id="sru-kernel-respins">
<span id="exp-sru-kernel-respins"></span><h2>SRU kernel respins<a class="headerlink" href="#sru-kernel-respins" title="Link to this heading">¶</a></h2>
<p>A respin is a rebuild of a kernel package replacing a previous build. During
each SRU cycle, kernel respins may need to happen for several reasons.</p>
<ul class="simple">
<li><p>A regression was introduced in a previous cycle or in the current cycle.</p></li>
<li><p>Additional fixes need to be added.</p></li>
<li><p>An important update needs to be added mid-cycle which cannot wait until the
next cycle.</p></li>
</ul>
</section>
<section id="kernel-streams">
<h2>Kernel streams<a class="headerlink" href="#kernel-streams" title="Link to this heading">¶</a></h2>
<p>Kernels that are ready for the full suite of testing and verification are
promoted to the “testing” phase, where the built kernel binaries (and artifacts)
are copied to a proposed location.</p>
<p>As the <a class="reference external" href="https://documentation.ubuntu.com/project/how-ubuntu-is-made/concepts/package-archive/#proposed">Ubuntu archive has a single proposed pocket</a>, the support for multiple
kernel streams was implemented in the kernel SRU workflow.
These streams consist of a set of locations (Ubuntu archive pockets or PPAs)
that can be used for parallel (and generally independent) preparation and
testing of kernels.</p>
<p>For example, when a respin is required for a regression released in the previous
cycle it can be prepared while the kernel spin for the current SRU cycle is
still in progress. These streams are also what enables the 4/2 Kernel SRU cycle
model.</p>
</section>
